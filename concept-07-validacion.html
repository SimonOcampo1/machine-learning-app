{ Tema 07 · Aprender de los datos }

Train/test y validación cruzada

Todo el tema responde una sola pregunta: cómo estimar honestamente qué va a hacer un modelo con datos que nunca vio. Es más difícil de lo que parece, y equivocarse acá invalida todo lo demás.

01

{ El problema }

Evaluar donde entrenaste no mide nada

Imaginá que estudiás para un examen con una guía de veinte ejercicios resueltos, y el examen resulta ser exactamente esos veinte ejercicios. Sacás diez. Ese diez no dice nada sobre si sabés la materia: dice que te acordás de la guía.

Un modelo hace lo mismo, pero con muchísima más capacidad de memorizar. Un árbol de decisión sin límite de profundidad puede aislar cada fila en su propia hoja y acertar el 100% sobre los datos de entrenamiento sin haber aprendido absolutamente ningún patrón general. El error de entrenamiento siempre se puede llevar a cero; eso lo vuelve inútil como medida.

Lo que querés saber es otra cosa: qué va a pasar con datos nuevos. Y la única forma honesta de estimarlo es apartar datos, no dejar que el modelo los vea, y recién al final preguntarle.

02

{ El corte básico }

Train y test

Se mezclan las filas al azar y se parte el dataset en dos: típicamente 75-80% para entrenar y 20-25% para testear. El modelo se entrena solo con la primera parte, y la segunda queda guardada.

X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.25, random_state=42)

El random_state fija la mezcla para que el corte sea siempre el mismo. Sirve para que un resultado se pueda reproducir; no cambia nada de la lógica.

La regla de oro es incómoda pero no tiene excepciones: el conjunto de test se usa una sola vez, al final de todo. No para elegir el algoritmo, no para ajustar hiperparámetros, no para decidir qué columnas incluir. En cuanto tomás una decisión mirando el test, dejaste de tener una estimación limpia, porque elegiste lo que mejor le queda a ese conjunto puntual.

CuidadoMezclar al azar es lo correcto salvo cuando los datos tienen orden temporal. Con series de tiempo, mezclar te deja entrenando con datos del futuro para predecir el pasado, que es imposible en producción. Ahí el corte es por fecha: se entrena con lo viejo y se testea con lo nuevo.
03

{ El tercer corte }

Validación

Si el test no se puede tocar, queda un problema práctico: casi todos los modelos tienen perillas que hay que elegir. Cuántos vecinos usa KNN, qué profundidad tiene un árbol, cuánto castiga Ridge. Esas perillas se llaman hiperparámetros, y no se aprenden de los datos: las elegís vos.

Para elegirlas hace falta comparar opciones, y comparar requiere evaluar. Si evaluás en test, lo quemás. La solución es un tercer corte: se parte el entrenamiento otra vez, y se aparta un conjunto de validación que sirve para tomar todas esas decisiones.

04

{ Cuando los datos son pocos }

Validación cruzada de k pliegues

El corte en tres tiene dos problemas cuando el dataset es chico. Primero, te quedás con muy pocos datos para entrenar. Segundo, y peor: el resultado depende de qué filas cayeron en validación. Con mala suerte, un corte distinto te habría hecho elegir otro modelo.

La validación cruzada resuelve las dos cosas. Se parte el entrenamiento en k pedazos iguales, llamados pliegues (típicamente 5 o 10). Después se entrena k veces: en cada vuelta, uno de los pliegues hace de validación y los otros k−1 de entrenamiento. Al final se promedian los k resultados.

El costo es que entrenás k veces en vez de una. Con modelos rápidos no importa; con redes neuronales grandes es prohibitivo, y ahí se vuelve a un corte simple.

Además, el desvío entre los k puntajes es información valiosa: si las cinco vueltas dan 0.81, 0.83, 0.80, 0.82 y 0.81, el modelo es estable. Si dan 0.65, 0.91, 0.72, 0.88 y 0.70, el promedio de 0.77 esconde que el resultado depende muchísimo de qué datos te tocaron.

05

{ Cuando las clases no están parejas }

Estratificación

Si el 5% de tus datos son fraude, un corte al azar puede dejarte un pliegue con el 1% y otro con el 9%. Peor: con clases muy raras, un pliegue puede quedarse sin ningún caso positivo, y entonces la métrica de esa vuelta no significa nada.

La estratificación arma los cortes cuidando que cada uno mantenga la misma proporción de clases que el dataset completo. En scikit-learn es un argumento: stratify=y en el split, o usar StratifiedKFold. Con clasificación desbalanceada no es opcional.

06

{ El error grande }

Fuga de datos

La fuga de datos ocurre cuando información del conjunto de test se cuela en el entrenamiento. El síntoma es siempre el mismo y es tramposo: resultados excelentes en tu evaluación, y un modelo que decepciona en producción.

El caso canónico es escalar antes de separar. Si calculás la media y el desvío sobre el dataset completo y después partís, esos dos números contienen información de las filas de test. El modelo entrenó en un espacio definido, en parte, por datos que se suponía que no conocía.

Error clásicoEl orden correcto es siempre: separar primero, después ajustar la transformación solo con train, después aplicarla a test. En scikit-learn eso es fit_transform sobre train y transform (sin fit) sobre test. Y con validación cruzada hay que rehacerlo en cada pliegue, lo cual es tan fácil de olvidar que existe Pipeline justamente para que no se pueda.

Hay formas más sutiles. Rellenar faltantes con la media global. Elegir qué columnas usar mirando su correlación con la respuesta sobre todo el dataset. Tener filas duplicadas que caen a los dos lados del corte. Y en series de tiempo, cualquier columna calculada mirando hacia adelante.

La pregunta que las detecta a todas es una: ¿esta información habría estado disponible en el momento de hacer la predicción real? Si la respuesta es no, es fuga.

08

{ Errores frecuentes }

Lo que más se rompe

TrampaUsar el test para elegir. Cada decisión tomada mirando el test le come un poco de honestidad a la estimación. Después de veinte comparaciones ya no queda nada: el número final es optimista y no hay forma de saber cuánto.
TrampaMezclar series de tiempo. Con datos ordenados en el tiempo, un corte al azar deja al modelo entrenando con el futuro. Los resultados salen espectaculares y son imposibles de reproducir en producción, porque ahí el futuro todavía no pasó.
Error clásicoEscalar antes de separar. Una sola línea, X = StandardScaler().fit_transform(X) puesta antes del split, y toda tu evaluación queda inflada. No tira error, no hay advertencia, y el modelo se ve mejor de lo que es. Es el error de fuga más frecuente y el más fácil de cometer, porque escalar primero es lo que parece ordenado.
09

{ Síntesis }

Lo que hay que llevarse

El error sobre los datos de entrenamiento siempre se puede llevar a cero memorizando, así que no mide nada: lo único que importa es el desempeño con datos nunca vistos, y para estimarlo hay que apartarlos antes de entrenar. El conjunto de test se toca una sola vez, al final, y cualquier decisión tomada mirándolo lo contamina; para las decisiones repetidas, como elegir hiperparámetros, está el conjunto de validación. Cuando los datos son pocos, la validación cruzada de k pliegues aprovecha todo el dataset entrenando k veces y promediando, y el desvío entre esos k puntajes dice si el modelo es estable o si el resultado depende de la suerte del corte. Con clases desbalanceadas los cortes tienen que ser estratificados, o algún pliegue puede quedarse sin casos de la clase rara. Y el error que invalida todo lo demás es la fuga de datos: información del test que se cuela en el entrenamiento, casi siempre por transformar antes de separar. La pregunta que la detecta es si esa información habría existido en el momento real de predecir. El próximo tema explica qué está pasando por dentro cuando el error de entrenamiento y el de test se separan, que es la tensión central de todo el machine learning.
